# 数学叙事设计

让学生带着一个具体、可理解、值得解决的问题学习，能说明每个新概念为何出现。借鉴 3Blue1Brown 的问题推进、几何直觉与视觉推导，不复制台词或固定镜头。

## 开始前

读取用户指定的学习目标、读者、正式前置、现有内容和项目教学规范。只审查或设计时不改代码；重构时遵守已授权文件范围。不把课程编号、提过的术语或折叠阅读当作已掌握知识。

本 Skill 可整目录复制到其他项目独立使用，不依赖另一个 Skill、Svelte 或本仓库文件。项目没有提供规范时，采用下述设计要求；读者与目标缺失时说明假设。

## 项目依赖门禁

执行前读取当地项目的 Skills 前置要求。本项目编写面向学生的课程内容时，必须先核实 math-storytelling、interactive-pedagogy、humanizer-zh 和 ui-ux-pro-max 的实际入口及所需资源；使用后两者分别润色中文和审阅课程 UX。任一缺失、不可读或不完整，暂停内容编写并要求用户安装或修复，复查成功后继续，不得降级替代。只读审查、Skills/规范/工具等非课程内容修改不受限制。移植到其他项目时遵守当地依赖要求，不把本机路径作为前提。

## 设计决策

1. 用一句可回答的问题界定本课。可以是几何构造、概率悖论或优化问题；工程/ML 场景应保留真实的量、约束和用途。不要为戏剧性制造失败，也不要给每个概念包装生活故事。
2. 列出“已学 → 本课新增 → 后续用途”，为每个新增概念指出旧方法的不足：算不出、表达不清、成本过高或无法推广。若旧方法已经足够，就解释新方法的表达或推广价值，不贬低旧方法。
3. 建立知识叙事链：**具体问题 → 初步尝试 → 遇到困难 → 新的观察 → 建立直觉 → 发现规律 → 数学表达 → 推广应用**。这是思考工具，可以合并、调序或省略不适用阶段；不要照搬成八个页面标题。保留问题、概念动机、论证和应用的联系。
4. 从能手算或看清的简单情形出发，选择会改变判断的对照与边界，再推广。让公式概括已经观察到的关系；必要的符号可以先引入，但须立即说明用途。尽可能给出几何或动态解释，并说明映射关系和失效边界；没有自然图像时用结构、表格或反例。
5. 在关键结论处标明“观察/猜想、直觉解释、证明、引用定理、近似”各自的地位。有限样本、拖拽和动画不能证明一般命题。给出必要逻辑步骤；引用定理须交代条件，不能用直觉跳过 ML 专有理论。
6. 为错误直觉设计可辨认的反例及解释；为结尾设计至少一个改变条件或表示方式的迁移挑战，要求解释理由，不能只替换数字。

## 交付给课程作者

按实际复杂度提供简短设计稿，包含：

- 核心问题、目标读者和前置边界。
- 阶段表：每行写“学生已知｜自然疑问｜为何引入下一步｜帮助理解的观察”。只写实际采用的阶段。
- 关键概念与公式的引入位置、符号/形状/单位、假设、推导或证明责任，以及直觉不适用的情况。
- 每个关键认识的预测问题与探索目标，交给交互设计继续细化；至少两个有意义的场景、两个误区/限制，以及迁移挑战和预期解释。
- 内容重排建议及保留理由；审查任务给出具体位置、学习障碍和最小修正，不默认重写全课。

检查学生能否沿着观察解释公式、用条件识别反例、把结论用于新情形。若主要教学仍依赖连续长文或答案在预测前已经泄露，调整学习路径。用自然简洁中文，保留必要英文术语；去掉空泛赞叹、机械排比和“神奇之旅”等开场。
