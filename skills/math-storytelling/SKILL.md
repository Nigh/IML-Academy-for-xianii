# 数学叙事设计

以现实任务优先：每课首先回答“一个还不知道本节数学概念的人，在什么具体情况下会遇到一个确实需要这个概念才能更好解决的问题？”让学生先理解要做什么、为什么现有方法不够，再学习数学工具。借鉴 3Blue1Brown 的问题推进、几何直觉与视觉推导，不复制台词或固定镜头。

## 开始前

读取用户指定的学习目标、读者、正式前置、现有内容和项目教学规范。只审查或设计时不改代码；重构时遵守已授权文件范围。不把课程编号、提过的术语或折叠阅读当作已掌握知识。

本 Skill 可整目录复制到其他项目独立使用，不依赖另一个 Skill、Svelte 或本仓库文件。项目没有提供规范时，采用下述设计要求；读者与目标缺失时说明假设。

## 项目依赖门禁

执行前读取当地项目的 Skills 前置要求。本项目编写面向学生的课程内容时，必须先核实 math-storytelling、interactive-pedagogy、humanizer-zh 和 ui-ux-pro-max 的实际入口及所需资源；使用后两者分别润色中文和审阅课程 UX。任一缺失、不可读或不完整，暂停内容编写并要求用户安装或修复，复查成功后继续，不得降级替代。只读审查、Skills/规范/工具等非课程内容修改不受限制。移植到其他项目时遵守当地依赖要求，不把本机路径作为前提。

## 现实任务优先（强制）

设计或审查开场时，必须先读 [开场准入与场景映射](references/scenario-design.md)，完成七项内部检查并维护场景—数学映射；开始编写课程前必须通过准入。第 1、2、5 项失败必须重设计；发现明显更好的替代场景必须采用；领域前提过重必须简化或解释。检查与映射是作者工具，不直接展示给学生。

按以下优先级寻找入口，不能先选公式再贴故事：

- **A：学生熟悉的现实任务。** 先考虑测量/比较/估算/校准，购物/成本/预算/资源分配，路程/速度/时间/运动，排列/组合/游戏策略/不确定性，图形/位置/角度/空间结构。
- **B：物理、工程或自然的 ML 任务。** A 不自然时，考虑电路的分压/滤波/阻抗/功耗，传感器/ADC/编码器的采样与标定，电机/轨迹/控制误差，信号的频率/相位/频谱，杠杆/齿轮/力矩/几何约束，机器人的坐标/姿态/路径/传感器融合，实验数据拟合/误差/统计推断，或读者能理解的 ML 需求。先解释不熟悉的术语及物理含义，不能用另一个专业抽象替代数学抽象。
- **C：数学本身的可操作问题。** 仅当现实场景会扭曲概念、增加不必要的知识负担或确无自然类比时使用；在设计稿记录原因，用简单具体例子、有限模型或可操作对象建立任务。集合论、逻辑、抽象代数和高维空间不必强套硬件故事。此时准入检查中的“场景”指这个具体数学任务，仍须有已知、目标、限制和可预测的结果。

禁止在缺乏背景时直接用“如何理解某概念/两个数学对象的关系/某定理”“为什么公式成立”“如何求某抽象量”作为初学者开场。这些可以在任务建立之后成为自然疑问。降低理解门槛是目的，现实类比本身不是目的。

## 先场景、后数学的设计流程

以下是每课必须保持的逻辑顺序，可以合并呈现，不必分别建页面或组件；不能调序到先讲目标概念、再补任务：

| 阶段           | 设计要求                                                                                                                                                    |
| -------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A 建立任务     | 用简短情境交代要做什么、已知信息、限制和期望结果；删掉不影响问题的背景故事。                                                                                |
| B 理解困难     | 通过自然问题、预测或简单实验发现现有方法的真实不足，不人为制造无意义障碍。                                                                                  |
| C 尝试已有方法 | 尽可能用直觉、简单算术、已学知识或已有工具尝试；接受近似、局部或不通用的答案。尝试可继续澄清 B 的困难；若旧方法已够用，诚实指出新工具在表达或推广上的价值。 |
| D 引入数学工具 | 确认学生已理解任务与困难后，才给目标概念、公式或定理；逐一解释关键量与任务的对应关系。                                                                      |
| E 回到原始任务 | 用新工具回答开场问题，与原方法比较，说明具体改善及代价。                                                                                                    |
| F 抽象和推广   | 从具体例子完整过渡到一般形式，说明条件、边界与必要论证；随后改变条件检验适用范围。                                                                          |

列出“已学 → 本课新增 → 后续用途”，为每个新增概念指出旧方法在计算、表达、成本或推广上的不足。必要辅助符号可提前定义并立即解释用途，但不能借此提前讲完目标知识。

叙事中的现实任务必须延续到学生的实际动作：设计稿写出“操作哪个对象 → 做什么 → 看见什么 → 数学如何解释 → 怎样用新条件验证”。现实操作建立直觉，数学视图解释规律，公式精确表达，不能把任务只留在开场文案或装饰插图中。交互方案优先操作现实对象或保留关键关系的简化模型，必要时联动数学视图；抽象对象作主界面须说明理由。对象准入、联动及实现细节由交互设计负责，本 Skill 不另设一套控件审查规则。

## 严谨性、反例与迁移

- 从能手算或看清的简单情形出发，用几何、动态过程、表格或反例帮助观察。公式需说明符号、形状、单位、取值域、假设与成立条件。
- 区分理想模型与真实系统、观察/猜想、直觉解释、证明、引用定理与近似。近似不写成精确等式；类比、有限样本、拖拽或动画不能证明一般命题。保留关键推理，引用定理交代条件，不跳过 ML 专有理论；明确类比失效的边界。
- 先把一个场景讲透，再改变参数、输入、约束或引入边界与看似相似但结论不同的情形。为错误直觉给出可辨认反例及原因，避免过早堆叠多个复杂领域案例。
- 至少一个迁移挑战要求学生选择方法、解释条件或判断适用性；只换数字并照套原公式不算迁移。

## 交付给课程作者

按实际复杂度提供简短设计稿，包含：

- 核心任务的已知/目标/限制、目标读者和前置边界；场景优先级的选择理由与准入检查结果（仅供作者）。
- 按 A–F 逻辑组织的阶段表与场景—数学映射：每行写“学生已知｜自然疑问｜为何引入下一步｜帮助理解的观察”；合并呈现时仍须覆盖各阶段的作用。
- 关键概念与公式的引入位置、符号/形状/单位、假设、推导或证明责任，以及直觉不适用的情况。
- 每个关键认识的预测问题与探索目标，交给交互设计继续细化；至少两个有意义的场景、两个误区/限制，以及迁移挑战和预期解释。
- 内容重排建议及保留理由；审查任务给出具体位置、学习障碍和最小修正，不默认重写全课。

检查学生能否沿着观察解释公式、用条件识别反例、把结论用于新情形。若主要教学仍依赖连续长文或答案在预测前已经泄露，调整学习路径。用自然简洁中文，保留必要英文术语；去掉空泛赞叹、机械排比和“神奇之旅”等开场。
